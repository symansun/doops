# 监控、巡检与资产感知闭环：设计任务书

编制日期 2026-11-22。状态：待评审，未实现。本文是设计任务书，不描述已上线行为；各任务落地时
再更新对应的权威文档（见 §11）。本文依赖 [Agent 资源同步与目标清单](AGENT_RESOURCE_SYNC.md)
（同为待评审），两者的先后关系见 §9。

## 1. 背景

2026-11-22 用本地真实 Gateway 与 Agent 对“智能综合感知运营、系统监控服务、智能巡检”三组共
44 个功能点做了验收，并逐项对照了源码。结论分四类：实测通过、部分实现、产品未提供、
有实现但本机没有数据源（下称“缺数据源”）。

产品未提供的有：探针自定义标签、探针覆盖率、磁盘 I/O、应用响应时间、并发连接数、错误率、
数据库事务。部分实现的集中在拓扑、探针部署、数据库连接数/查询性能/锁等待、敏感操作、
可疑进程、配置合规、Web 安全、API 巡检。缺数据源的有 GPU、业务请求量、数据库监控、
异常登录、权限变更、全部漏洞与补丁项、数据库状态、流量异常。

多数功能只做了“判定”这一段，前面缺取数，后面缺处置，因此没有闭环。本文先说明造成这一
结果的架构原因，再给出统一方案和逐项设计。

## 2. 设计依据的架构事实

以下各条均来自当前代码与权威文档，是本设计必须遵守的边界。

### 2.1 角色

| 角色 | 职责 | 与本设计相关的约束 |
| :--- | :--- | :--- |
| Gateway | 用户认证、目标授权、审计、路由，SQLite 持久化 | 单活；没有调度器，契约禁止重新引入；不主动连入内网 |
| Agent | 在目标网络内执行工具调用并返回证据 | 只有出站长连接；本地不建数据库；不持有 Gateway 用户 token |
| Web 控制台、CLI | 两种入口，共用一次 Gateway 登录 | 浏览器 token 在 HttpOnly 会话里，页面不自行判定权限 |

依据：[隧道文档](../DOOPS_GATEWAY_TUNNEL.md)、[统一运维工作台](../UNIFIED_OPERATIONS_WORKBENCH.md)、
仓库 `AGENTS.md` 的 Canonical Architecture。

### 2.2 授权与身份

- 授权单位只有 `(user, cluster, instance)`。有目标授权即可做该目标上的全部操作。不得新增按操作、
  按资源、按指标的权限维度。
- 一台机器有三个标识：`asset_id`（台账）、`cluster/instance`（可授权的 Agent 目标）、
  `host_sha256`（宿主 machine-id 的指纹）。首次绑定须由平台管理员核验指纹
  （[宿主采样](../MACHINE_SAMPLING.md)）。
- 资产与目标的关系只存在 Gateway 的台账里。Agent 不知道自己对应哪些资产。

### 2.3 Agent 能看到什么

Agent 的接入模式决定可观测范围（模式定义见资源同步任务书 §3）。

| 接入模式 | 可直接观测 | 观测不到 |
| :--- | :--- | :--- |
| `kubernetes` | 集群 API；所在节点的宿主（Helm 默认 `hostAccess.enabled=true`：共享宿主 PID、只读挂载 `/host`） | 其它节点的宿主内核与进程；hypervisor |
| `docker` | 所在宿主（取决于容器挂载与权限） | 其它主机 |
| `linux` | 所在宿主 | 其它主机 |

到其它主机只有一条现成路径：结构化 `doops_ssh`，由 Agent 向已知主机发起。它要求 Agent 执行环境
已有认证材料和已核验的主机密钥。凭据系统没有通用 SSH 凭据注入
（[物理机访问](../PHYSICAL_HOST_ACCESS.md)）。机器登录保险库（scope `machine_login`）由 Gateway
加密保存，通用凭据 API 不能管理它；编制本文时没有找到把它下发到 Agent 的代码路径。

### 2.4 已有的证据规则

现有监控与巡检代码已经形成一组一致的规则，本设计沿用而不改写：

- 缺测不等于正常。样本状态分 `ok`、`missing`、`not_applicable`；巡检结论分 `pass`、`finding`、
  `insufficient`、`missing`，缺口保留原因。
- 采集时刻重新核对绑定。巡检在取证时检查执行账号授权、资产绑定和目标在线；宿主取样检查
  领取凭据与连接 generation。
- 判定不依赖 Gateway 时钟。阈值告警在样本写入时计算（`asset_monitor_store.go`）；巡检的逾期与
  漏检在读取时由截止时间推导。
- 采集只读。所有采集脚本只读取 `/proc`、包数据库、日志和 HTTP 端点，不改变目标。
- 输出只含元数据和脱敏数值，不含凭据、响应正文或业务字段原值。

## 3. 现状：三条互不相通的取数路径

| 路径 | 谁发起 | 身份 | 承载内容 | 断点 |
| :--- | :--- | :--- | :--- | :--- |
| 拉取 | 用户在控制台点一次 | 用户会话，经 Gateway 调 Agent 工具（`doops_k8s top`、`doops_machine_diagnostic_sample`） | Pod CPU/内存；宿主快照 | 没人点就没有数据，形不成曲线 |
| 推送 | 宿主上的 `asset_monitor_collector.py` 加 systemd 定时器 | 平台管理员 token，经“受控中心”提交 `ingest` | 机器、内核、进程、网卡、挂载点、GPU、nginx 请求数 | 每台机器手工部署；写入需要管理员 token；Agent 不参与 |
| 巡检 | 独立执行器 `inspection/runner.py`，每五分钟 | 计划绑定的普通执行账号 token | 读取证据目录里的 `M*.json`、`A*.json`、`sbom.json` 后提交 | 证据由另外的生产器写文件，目录要挂载给执行器；任何一环没部署就是缺数据源 |

由此产生四个后果，对应验收里的全部缺口：

1. **采集不归 Agent 管。** Agent 是唯一已在目标网络内、已认证、已审计的进程，但持续采集绕开了它。
   于是“探针部署”变成逐台手工操作，“探针覆盖率”也无从统计。
2. **指标集合写死。** `monitorUnits` 与建表约束只允许 8 个指标名，磁盘 I/O、连接数、错误率、
   数据库指标没有位置。
3. **同一事实采两遍。** 监控和巡检各有采集器；M2 读监控序列，其余巡检项读文件。安全、漏洞类
   观测只在巡检里出现，监控页看不到。
4. **判定之后没有下文。** 告警只写入 `asset_monitor_alerts`，没有通知；巡检发现项可以登记整改
   和复检，但与告警不在同一个待办里，也没有负责人和时限。

## 4. 设计原则

1. Agent 是观测事实的权威方，Gateway 是登记事实的权威方。这与资源同步任务书一致。
2. 时钟放在 Agent。Gateway 不调度，只在收到观测和被读取时判定。
3. 一份观测，多处使用。监控曲线、巡检判定、拓扑关系、覆盖率都读同一批观测。
4. 采集范围由台账决定并下发，Agent 不自行扩大范围，也不猜测资产。
5. 授权模型不变。读取跟随目标授权；不新增权限维度。
6. 采集只读、输出只含元数据。新增的每条输出路径都用合成 canary 断言不出现凭据载荷。
7. 说不清的就标缺口。观测不到、范围外、源过期都如实呈现，不显示为正常。
8. 现有三条路径保持可用，作为兼容入口，直到新路径在同一目标上验收通过。

## 5. 目标模型

### 5.1 概念

| 概念 | 定义 | 权威方 |
| :--- | :--- | :--- |
| 采集配置 | 某个目标应当观测哪些资产、哪些项、多长间隔 | Gateway 由台账生成，随目标清单下发 |
| 采集器 | Agent 进程内按采集配置定时运行的只读取数逻辑 | Agent |
| 观测 | 采集器的一次产出，带资产标识、观测时间、来源和状态 | Agent |
| 判定 | Gateway 对观测套用阈值、策略或基线得出的结论 | Gateway |
| 事件 | 一次未恢复的告警或一个未关闭的巡检发现项 | Gateway |

观测分四种形态，共用一个上行信封：

| 形态 | 内容 | 例子 | 落库 |
| :--- | :--- | :--- | :--- |
| 样本 | 数值加单位 | CPU、磁盘 IOPS、连接数 | 现有 `asset_monitor_samples` |
| 状态 | 一份带摘要的事实快照 | 已装软件包、sysctl 与 sshd 生效配置、账号与特权组文件摘要、监听端口 | 新表，按摘要去重，只在变化时存新版本 |
| 计数窗口 | 一个时间窗内的事件计数 | 登录失败次数、4xx/5xx 次数 | 作为样本落库，窗口起止写入来源 |
| 探测 | 对一个端点的一次检查结果 | HTTP 状态与耗时、TLS 证书、数据库探活 | 耗时与结果作为样本，失败原因作为缺口 |

### 5.2 采集器按接入模式分工

| 对象 | `kubernetes` Agent | `docker` / `linux` Agent | 没有 Agent 的主机 |
| :--- | :--- | :--- | :--- |
| Agent 所在宿主 | 经宿主 PID 视图与 `/host` 读取；进入前沿用[物理机访问](../PHYSICAL_HOST_ACCESS.md)的固定核验 | 直接读取 | 不适用 |
| 集群内其它节点 | 节点与 Pod 资源用 kubelet Summary API（经 API Server）；内核、进程、安全类观测需要 §12 D2 的方案 | 不适用 | 不适用 |
| Pod 与工作负载 | 集群 API，替代现在逐次手动的 `kubectl top` | 不适用 | 不适用 |
| 远端主机 | 结构化 SSH，使用只读采样账号，见 §12 D1 | 同左 | 由可达的 Agent 代采 |
| 应用端点 | Agent 发起 HTTP/TLS 探测 | 同左 | 由可达的 Agent 代采 |
| 数据库 | 复用 DoSql 的发现结果与目标上已绑定的数据库凭据，执行固定的只读状态查询 | 同左 | 由可达的 Agent 代采 |
| GPU | 宿主 `nvidia-smi`；集群内已有 DCGM exporter 时抓取 | 宿主 `nvidia-smi` | SSH 执行 `nvidia-smi` |

“探针”在本设计里指**一台机器的有效采集通道**，而不是一个必须安装的进程。Agent 所在宿主天然有
通道；其它机器通过上表中的某一种方式获得通道。

### 5.3 上行：观测上报（Agent → Gateway）

复用资源同步任务书 §4.1 的上行通道，增加周期性观测帧。

- Agent 每个采集周期（默认 60 秒）把本周期的观测打成一批上报。批内每条带 `asset_id`、形态、
  指标或检查项、观测时间、状态和来源。
- 身份是 Agent 的领取凭据，不是用户 token。Gateway 只接受已领取、在线、generation 匹配的连接
  上报的观测，并且只接受采集配置里列出的 `asset_id`。范围外的条目整批拒绝并记录原因。
- 断连期间 Agent 在内存里保留有限的最近观测（建议最多 15 分钟），重连后补报；超出部分丢弃，
  Gateway 侧表现为中断。不在 Agent 落盘，不建本地库。
- 周期性观测不逐条写审计。审计记录采集配置的变更、范围拒绝和采集器启停。每条序列保存来源
  （连接 generation、清单版本），用于回溯。

### 5.4 下行：采集配置（Gateway → Agent）

采集配置是目标清单的一个组成部分，随清单版本下发，不另建通道。

```json
{
  "collection": {
    "interval_seconds": 60,
    "assets": [
      {"ref": "machine/SRV-001", "channel": "local_host", "packs": ["host", "disk", "security"]},
      {"ref": "machine/SRV-002", "channel": "ssh", "host_ref": "ssh/SRV-002", "packs": ["host", "disk"]},
      {"ref": "system/orders", "channel": "probe", "checks": ["A1", "A4", "A5"]},
      {"ref": "database/orders-mysql", "channel": "database", "credential": "credential/orders-ro"}
    ]
  }
}
```

- 配置只含引用名、通道和采集包名。端点 URL、阈值之外的策略参数按资产随配置下发；凭据只出现
  资源名。
- 采集包是一组固定的只读观测，随 Agent 版本发布，不接受调用方传入的命令。
- 台账、标签、巡检计划或凭据绑定变化时清单升版，Agent 下一个周期按新配置采集。

### 5.5 判定

- **阈值**：沿用现有“超过阈值并持续一段时间”的规则，在样本写入时计算。增加按标签或资产类型
  生效的默认规则，免去逐条序列设置。
- **策略**：巡检项的判定逻辑不变（`inspectionVerdict`）。变化在于证据来源：Gateway 从取证窗口内
  的观测生成收据，不再等执行器读文件提交。收据仍保存来源摘要和策略摘要。
- **基线**：流量异常增加“过去 N 周同一星期同一小时”的统计基线，历史不足时结论为
  `insufficient`。静态上下限继续作为硬边界。
- **周期**：巡检计划的周期推进仍由一次写入触发。计划范围内任一目标的 Agent 上报到期观测时，
  Gateway 在同一事务里对账到期周期。长期没有观测到达的计划，在读取时显示为逾期，由管理员
  冻结漏检清单。这一点改变了现有“执行器发 tick”的做法，见 §12 D3。

### 5.6 事件闭环

所有功能点共用一条处置路径：

```text
接入 -> 采集 -> 展示 -> 判定 -> 事件 -> 通知 -> 认领与整改 -> 复检 -> 关闭 -> 报表
```

- 事件有两个来源：未恢复的阈值告警、未关闭的巡检发现项。合并为一个列表，不合并底层表。
- 事件的负责人默认取业务系统台账里登记的负责人；机器类事件取巡检计划的责任人。
- 整改沿用巡检已有的“登记整改、新 generation 复检”。阈值告警的复检就是恢复：指标回落后自动
  关闭并保留时长。
- 登记整改后，下一批到达的观测即作为复检证据，不需要人工再次触发取证。
- 通知是 Gateway 的新增出站行为，见 §12 D5。

### 5.7 存储

样本量估算（估算值，未实测）：一台机器约 30 条序列，60 秒一个点，每天约 4.3 万行；500 台约
2,160 万行。SQLite 单库不能长期保存这个量的原始点。

| 层 | 粒度 | 保留 | 生成方式 |
| :--- | :--- | :--- | :--- |
| 原始 | 采集周期 | 7 天（与现有查询范围一致） | 上报写入 |
| 5 分钟汇总 | 最小、最大、平均、计数 | 30 天 | 写入原始点时同事务更新所在桶 |
| 1 小时汇总 | 同上 | 1 年 | 同上 |

汇总在写入时增量维护，不需要调度。过期清理并入 Gateway 已有的每小时清理循环。状态类观测按
摘要去重，只在内容变化时新增版本。指标名从建表约束改为注册表：名称、单位、允许的设备维度和
取值范围，新增指标不再需要改约束。

### 5.8 安全边界

- 采集包只读。任何需要写目标的动作（安装补丁、改配置、下发探针）不属于采集，走已有的受审计
  执行路径并单独授权。
- 状态类观测只保存摘要与脱敏字段。账号文件保存用户名、UID、组成员和文件摘要，不保存口令散列；
  慢查询保存指纹与耗时，不保存 SQL 字面值；访问日志只保存计数。
- 数据库采集使用目标上已绑定的数据库凭据，经现有的内部物化路径，载荷不进入采集配置、观测或
  日志。
- 上报、清单、观测落库、控制台展示、导出五处都要有合成 canary 测试。

## 6. 逐项设计

表中“来源”一栏的通道名对应 §5.2。“现状”取自验收结果。

### 6.1 智能综合感知运营

| 功能点 | 现状 | 来源与观测 | 判定与页面 | 闭环补齐 |
| :--- | :--- | :--- | :--- | :--- |
| 资产分层拓扑 | 部分：K8s 关系实时，业务与物理关系靠人工登记 | 状态观测：监听端口与已建立连接（主机）、工作负载与 Service（集群）、虚拟化类型 | 推断出的“应用到数据库”“虚机到宿主”关系列为候选，管理员确认后成为登记关系；节点上显示未关闭事件数 | 事件可跳到拓扑查看受影响的业务系统；候选关系有确认和驳回 |
| 服务器与业务系统覆盖率≥80% | 缺数据源：未建立基线 | 不新增采集，沿用底册与冻结基线 | 缺口清单每行给出“去接入”入口；增加按批次的趋势 | 达标批次可导出验收报告；缺口有负责人 |
| 监控-机器 | 通过 | 样本：CPU、内存、网卡、挂载点；在线状态由采集中断推导 | 机器详情 | 采集中断超过 5 分钟成为事件，恢复后自动关闭 |
| 监控-操作系统 | 通过 | 样本：负载、运行时长；状态：OS 版本 | 详情“系统”一节 | OS 版本变化记入变更历史 |
| 监控-内核 | 通过 | 样本：内核 CPU、Slab、`oom_kill` 计数 | 详情“内核”一节 | OOM 计数增长成为事件 |
| 监控-进程 | 通过 | 样本：按 PID 加启动时间；增加按服务名登记 | 进程列表与曲线 | 被监控进程消失成为事件 |
| 监控-应用 | 部分：只测到进程级 | 集群通道取 Pod 资源；主机应用按已核验的服务 cgroup 聚合 | 应用视图同屏显示资源与业务指标 | 事件带业务系统负责人 |
| 监控-数据库 | 缺数据源 | 数据库通道，指标见 §6.2 | 数据库详情 | 探活失败成为事件 |
| 指标-CPU / 内存 | 通过；CPU 单位是 cores | 不变 | CPU 同时显示 cores 和占登记核数的百分比 | 默认阈值规则 |
| 指标-GPU | 缺数据源 | 样本：每卡利用率、显存已用与总量、温度 | 多卡分别展示 | 显存与温度阈值 |
| 指标-网络流量 | 通过 | 样本：收、发分开；网卡自动枚举后由采集配置固定 | 网卡曲线 | 错误包与丢包计数阈值 |
| 指标-业务请求量 | 缺数据源 | 计数窗口：nginx `stub_status` 或访问日志；外部 exporter | 业务系统页 | 未配置来源时页面写明“未配置数据源”并给出配置入口 |
| 指标-存储容量 | 通过 | 样本：总量、已用、可用 | 使用率与按近期增速推算的写满天数 | 推算天数低于下限成为事件 |

### 6.2 系统监控服务

| 功能点 | 现状 | 来源与观测 | 判定与页面 | 闭环补齐 |
| :--- | :--- | :--- | :--- | :--- |
| 探针部署 | 部分：无批量下发 | 不再逐台安装。机器在台账绑定目标并选定通道后，采集配置自动包含它 | “接入”页：按机器显示通道、最后观测时间、失败原因；可多选机器批量指定通道 | 通道失败有明确原因和重试 |
| 探针自定义标签 | 未提供：现有机器标签是平面文本 | 机器标签扩展为 `key=value`；标签属于台账，随观测的 `asset_id` 关联到序列，不另存一份 | 监控、巡检范围、覆盖率、事件都可按标签筛选和分组 | 巡检计划可按标签选范围，新机器自动纳入 |
| 探针机器覆盖率 100% | 未提供 | 分母：冻结基线内的在役机器；分子：最近 5 分钟内有有效观测的机器 | “接入”页顶部显示比例和缺口清单；可导出 | 豁免须管理员填写原因并计入报告 |
| 系统级-CPU / 内存 / 网络 | 通过 | 同 §6.1 | 同 §6.1 | 同 §6.1 |
| 系统级-磁盘 I/O | 未提供 | 样本：`/proc/diskstats` 差分，得每盘读写 IOPS、吞吐、平均等待、繁忙度 | 机器详情“磁盘”一节 | 等待时间阈值 |
| 应用级-响应时间 | 未提供 | 探测耗时；有访问日志时取 P95 | 应用视图 | 阈值；与 A1 共用同一次探测 |
| 应用级-并发连接数 | 未提供 | 样本：`stub_status` 的活跃连接数（采集器已读取该页面，只取了请求计数） | 应用视图 | 阈值 |
| 应用级-请求速率 | 缺数据源 | 同业务请求量 | 同上 | 同上 |
| 应用级-错误率 | 未提供 | 计数窗口：访问日志的 4xx、5xx 与总数；无日志时用探测失败率并标明口径 | 应用视图 | 持续超阈值成为事件 |
| 数据库-连接数 | 部分：只分析提交的样本 | 样本：当前连接数、上限、使用率（MySQL 全局状态、PostgreSQL `pg_stat_activity`、MongoDB `serverStatus`） | 数据库详情曲线 | 使用率阈值 |
| 数据库-查询性能 | 部分 | 样本：慢查询计数差分；状态：按指纹的 Top 慢语句 | 趋势与 Top 列表 | 事件可带入 DoSql 分析 |
| 数据库-事务处理 | 未提供 | 样本：提交与回滚计数差分得 TPS 与回滚率；状态：长事务列表 | TPS 曲线 | 长事务超时成为事件 |
| 数据库-锁等待 | 部分：只解析慢日志 | 样本：锁等待次数与时长；状态：当前阻塞关系 | 阻塞链 | 阻塞超时成为事件 |
| 安全-异常登录 | 缺数据源：依赖 Linux Audit | 计数窗口：优先 Audit；没有 Audit 时读取系统日志的认证记录，并在来源里写明口径 | 安全视图：失败次数、来源地址、首次出现的来源 | 窗口内失败次数超限成为事件 |
| 安全-权限变更 | 缺数据源；直接改文件不覆盖 | 状态：账号、组、sudoers 文件的摘要与结构化成员；Audit 组管理记录 | 两次状态之间的差异 | 每次差异成为事件，须有人确认为已知变更 |
| 安全-敏感操作 | 部分：只有 DoOps 自身通道 | DoOps 审计沿用；主机有 Audit 规则时取命中计数 | 两个来源合并展示并标明来源 | 没有 Audit 的主机显示“未覆盖”，不显示为正常 |

### 6.3 智能巡检

巡检项编号、结论类别、整改与复检流程都不变。变化是证据从观测生成。

| 检查 | 现状 | 证据来源 | 判定变化 | 闭环补齐 |
| :--- | :--- | :--- | :--- | :--- |
| M1 运行与重启 | 通过 | 主机采集包的启动时间与运行时长 | 不变 | 异常重启成为事件 |
| M2 CPU 与内存 | 通过 | 现有序列 | 不变 | 同上 |
| M3 可疑进程 | 部分：只测未命中 | 状态：进程短名、可执行文件路径是否已删除、是否位于临时目录 | 拒绝列表之外增加上述规则；不做行为分析 | 命中项可确认为合法并加入该资产的允许列表 |
| M4 配置合规 | 部分：5 类 sysctl | 状态：sysctl、`sshd -T` 生效配置、口令策略文件、关键文件权限、时间同步状态 | 策略改为可扩展的基线包，按标签下发 | 不合规项给出期望值 |
| M5 登录与权限变更 | 缺数据源 | 同安全-异常登录、权限变更 | 没有 Audit 时不再必然留缺口，改按系统日志口径判定并标明 | 周报汇总 |
| V1 应用漏洞 | 缺数据源 | 状态：软件包清单（`dpkg-query`，新增 `rpm`）；集群内容器镜像清单 | 版本比较增加 rpm 规则；公告仍由维护方签发并同步 | 发现项成为事件 |
| V2 补丁检查 | 缺数据源 | 同上 | 不变；不自动安装 | 生成待办并指派 |
| V3 修复验证 | 缺数据源 | 登记整改后到达的下一份软件包清单 | 不变 | 通过后事件自动关闭 |
| A1 服务可用性 | 通过 | 探测 | 增加“连续 N 次失败”条件，避免单点抖动 | 同上 |
| A2 数据库状态 | 缺数据源：依赖外部 exporter | 数据库通道直接探活；exporter 保留为备选 | 不变 | 同上 |
| A3 流量异常 | 缺数据源；只有静态上下限 | 请求速率序列 | 增加 §5.5 的统计基线 | 历史不足时为 `insufficient` |
| A4 Web 安全 | 部分 | 探测：证书链、剩余天数、TLS 版本、安全响应头 | 增加证书到期与更多响应头 | 主动漏洞探测见 §12 D6，不进入默认周检 |
| A5 API 巡检 | 部分：只测不匹配 | 探测 | 增加请求方法、请求头、凭据引用和耗时上限 | 失败附脱敏的响应摘要 |

### 6.4 验收中未覆盖的五项

| 项 | 在本设计中的归属 |
| :--- | :--- |
| 定时自动调度 | 时钟在 Agent 采集器；不再依赖独立执行器的定时器 |
| 导出内容 | 覆盖率、巡检报告、事件清单统一为可下载的验收材料，按读取时的授权过滤 |
| 修复后重新取证 | §5.6：整改登记后到达的观测即复检证据 |
| 离线恢复 | Agent 重连后补报有限的最近观测；更早的部分保留为中断 |
| 多用户权限 | 读取跟随目标授权，不新增维度；需用两个不同授权的账号做对照验收 |

## 7. 控制台信息架构

保留“平台监控”现有五个页签：概览、拓扑、监控、巡检、覆盖率。新增两个：

- **接入**：每台机器的通道、最后观测时间、失败原因、标签；顶部是探针覆盖率与缺口。
- **事件**：未恢复告警与未关闭发现项的统一列表，带负责人、时限、状态和处置入口。

资产详情按层分节：机器、系统与内核、磁盘、进程、应用、数据库、安全。不为单个指标新建页面。
每个视图都要有加载、空、错误、无权限四种状态；“未配置数据源”“范围外”“源已过期”分别显示。

## 13. 验收场景

- Given 一台已绑定目标并核验指纹的机器，When Agent 在线且无人操作控制台，Then 十分钟后该机
  CPU、内存、磁盘曲线各有连续的点。
- Given Agent 上报了采集配置之外的 `asset_id`，When Gateway 收到该批，Then 整批拒绝并留下
  审计，不写入任何样本。
- Given 用户只有目标 A 的授权，When 读取事件、曲线和导出，Then 只包含目标 A 关联的资产；撤权后
  同一请求返回为空或 403。
- Given Agent 断连 30 分钟后重连，When 查看曲线，Then 最近一段有补报的点，更早的一段显示为
  中断，没有被填平。
- Given 一台没有 Linux Audit 的主机，When 查看敏感操作，Then 显示“未覆盖”及原因，不显示为
  无异常。
- Given 一个 V1 发现项已登记整改，When 下一份软件包清单到达且版本达到修复线，Then 该项通过，
  对应事件关闭，报告保留前后两份收据。
- Given 基线内 100 台在役机器中 3 台最近 5 分钟没有有效观测，When 打开“接入”页，Then 探针
  覆盖率为 97%，缺口清单列出这 3 台及各自的失败原因。
- Given 数据库采集使用合成 canary 口令，When 检查清单、上行帧、落库内容、页面和导出，Then 五处
  都不出现该值。
