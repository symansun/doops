# dev / 114 DoOps Agent Deployment

This document records the stable deployment boundary for the dev Kubernetes
environment. It intentionally excludes the host address, passwords, private
keys, kubeconfig contents, registry credentials, and Gateway tokens.

## Environment Identity

- Local SSH recovery alias: `dev` or `dev-114`
- DoOps target: `gw-114-k8s`
- Gateway identity: `doops-114-k8s/master-1`
- Kubernetes namespace: `kube-system`
- Agent workload: `deployment/doops-agent-gateway`
- Agent container: `doops-agent`
- Gateway URL: `https://doops.l8ai.cn`

The SSH alias is maintained only in the operator's local `~/.ssh/config`.
Normal operations use the DoOps target. SSH is reserved for initial bootstrap
and Agent recovery when the installed Agent cannot execute the current
structured Kubernetes protocol.

## Preflight

Only during bootstrap or Agent recovery, verify local key-based recovery access
without prompting for a password; this is not a normal deployment prerequisite:

```bash
ssh -o BatchMode=yes dev \
  'hostname && kubectl -n kube-system get deployment doops-agent-gateway'
```

Verify the Gateway route:

```bash
doops -session dev-114-preflight targets --target gw-114-k8s
```

Before changing the workload, record the current immutable image with the
read-only DoOps Kubernetes interface and confirm the candidate image was
produced by a successful `main` CNB build. Do not deploy a floating tag.
Ordinary workload releases use `doops -session <session> ask --target
gw-114-k8s --apply` and do not require a local kubeconfig.

## Upgrade

If the live Helm Agent contains the in-cluster self-upgrade controller, run
`doops upgrade` against `gw-114-k8s` with an immutable image digest. The
in-cluster Job reuses the kubeconfig already mounted in the Agent, so the
operator machine does not need a kubeconfig. The CLI waits for the Job,
verifies the Gateway handoff and `structuredSSH`, and starts a rollback Job
when the probe fails.

The Agent must mount a shareable `/root/.kube` or `/root/.kube/config` volume and
have the cluster permissions needed by the Job. Repository changes alone do not
prove that the installed CLI, Gateway, or live Agent has this controller.

Use `scripts/release-managed-agent.sh` with an approved temporary kubeconfig
only if this target is being adopted onto the Helm chart through a separately
reviewed bootstrap, the current Helm Agent predates the self-upgrade controller,
or runtime values are being explicitly changed. The existing-target path requires
an existing Helm release and does not perform automatic adoption.

SSH may transport an approved kubeconfig into a protected temporary file on the
operator machine, but SSH must not patch the workload or serve as deployment
evidence. Delete the temporary kubeconfig after the external controller exits.

## Verification

Verify the public control path and read back the actual image, rollout state,
Pod readiness, imageID, and restart count:

```bash
doops -session dev-114-verify targets --target gw-114-k8s
doops -session dev-114-verify exec --target gw-114-k8s \
  --cmd 'do-agent --version && kubectl get nodes'
doops -session dev-114-verify k8s get pods --target gw-114-k8s \
  --namespace kube-system --output wide
```

The deployment is complete only when the workload is ready, the Pod `imageID`
matches the requested digest, the target reconnects to Gateway, and both
`exec` and structured `k8s` reads succeed.

## Rollback

For `doops upgrade`, the in-cluster Job attempts rollback to the revision recorded
before mutation when rollout fails; the CLI requests a rollback Job when the
protocol probe fails. The external script has its own rollback path for existing
Helm releases; new-cluster bootstrap does not provide the same guarantee.
Report rollback failure explicitly and verify the restored Deployment image,
readiness, and Gateway connection before declaring recovery. Never roll back to
a floating tag or restore credentials from repository files.
