# 任务闭环标准（lead 强制，2026-11-24 起适用于所有子会话）

用户要求：「每个任务要彻底闭环」。以下七条是"完成"的定义，缺一条不算完成，不得以"后续跟进"交付。

1. **权威文档先于/同于代码**：改动必须能指到唯一权威文档的具体条款（如 `backend/docs/design/SKILL_FIRST_INSPECTION_SPEC.md §3.2`）。文档与实现不一致时，同一个提交里改到一致——不允许"代码这样、文档那样"地留到下一轮。
2. **代码与测试同批入库**：测试必须能复现问题（改坏实现要红，恢复要绿）。报告里必须写出至少一次**反向实验**：你改坏了哪一行、失败输出摘要。
3. **在干净树上验证**：`git archive <你的 sha> | tar -x -C /tmp/x` 里跑 build/vet/测试，不拿共享工作区（含他人未提交改动）当证据。
4. **用户可见变化写 `CHANGELOG.md` 的 `## [Unreleased]`**（前端/文档会话或我指定的 owner 写；他人不得改该文件）。CLI/接口变化同步 `--help` 与对应 API 文档。
5. **证据分级写清**：真跑（容器/真机/浏览器）> 单测 > 静态断言 > 未覆盖。未覆盖必须显式列出，并写明"为什么这次做不了"和"谁来补"。
6. **零悬空尾巴**：本轮发现的缺陷只有两个出路——当轮修掉，或写进 `docs/operations/backlog.md` 并带 owner + 验收条件。禁止"已知问题，后续处理"式收尾。
7. **推送即完成**：`ahead=0`，报告给出 sha、实际执行的命令与结果摘要、改库/schema 影响、未覆盖清单。共享索引纪律：`git commit -o <自己的路径>` 或暂存即提交。

## 派活时必须写进任务书的四件事

- 拥有文件清单 + 禁改文件清单（`components/`、`lib/`、`package.json`、`pnpm-lock.yaml`、`CHANGELOG.md`、`docs/operations/**` 的归属）；
- 验收命令（含 `env -u GOROOT`、干净归档、反向实验）；
- 四段式提交模板（标题/正文/Spec:/Tests:/Co-Authored-By）；
- 闭环出口：哪份文档要同步、CHANGELOG 谁写、遗留项怎么落到 backlog。
